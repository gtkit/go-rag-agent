## Context

当前库已经具备：
- `Session` 短期历史
- 历史 token 预算与本地摘要压缩
- 检索、工具、结构化输出、执行 trace

但短期历史仍然只适用于最近窗口内的上下文。窗口外的信息无法被语义检索，只能依赖摘要在 prompt 中保留极少部分。对真正的 agent 使用场景来说，这还缺少“长期记忆层”。

本轮实现目标不是做完整的人类式记忆系统，而是在现有架构上增加一个最小可用的、可插拔的长期语义记忆层。

## Goals / Non-Goals

**Goals:**
- 在根包公开长期记忆接口与数据类型
- 在成功问答后写入长期记忆
- 在后续问答前按查询检索同 Session 的长期记忆并回灌 prompt
- 提供默认 `in-memory` 实现，证明接口和主流程可用

**Non-Goals:**
- 不实现跨 Session 共享记忆
- 不实现跨进程持久化长期记忆
- 不实现复杂记忆类型（事实/情景/程序化）分层

## Decisions

### 1. 长期记忆只做同 Session 语义检索

第一版长期记忆按 `sessionID` 隔离，只在当前 Session 内召回旧轮次。这样既能补足“超出短期窗口的旧信息找回”，又不引入跨会话污染和更复杂的多租户语义。

### 2. 长期记忆接口独立于 VectorStore

虽然语义检索可以复用向量搜索思想，但长期记忆的记录模型与知识分块不同，因此使用独立接口：
- `Store`
- `Search`
- `ClearSession`
- `Close`

这样不会强行把记忆层塞进当前 `VectorStore` 语义里。

### 3. 默认实现先用 in-memory

第一版默认实现使用进程内存保存长期记忆记录并做向量相似度检索。这样可以快速验证：
- 接口是否合理
- 主流程是否正确
- 记忆写入/召回语义是否稳定

后续如果需要，可再加 pgvector 或其他存储实现。

### 4. 长期记忆写入基于问答完成后的整轮内容

每次成功问答后，将：
- 用户 query
- 助手 answer
- `sessionID`
- 时间戳
- 嵌入向量

写入长期记忆。检索时使用当前 query embedding 与这些历史记录的 embedding 做相似度匹配。

### 5. prompt 中单独注入 “Relevant long-term memory”

长期记忆不与即时证据混在一个字段里，而是在 prompt 中单独作为：
- `Relevant long-term memory: ...`

这样可以保留“当前知识证据”和“过去对话记忆”的语义边界。

## Risks / Trade-offs

- [in-memory 默认实现不能跨进程持久化] → 第一版接受；后续可追加持久化实现
- [同 Session 限制减少复用价值] → 先保证无污染和语义稳定，后续再扩展跨 Session
- [长期记忆回灌增加 prompt 体积] → 受现有 prompt budget 限制约束，并给长期记忆单独预算
