## Context

当前 PDF 导入链路只处理文本型 PDF：
- `source.go` 已允许 `.pdf` 进入导入流程
- `internal/rag/loader.go` 会直接抽取 PDF 文本
- 当 PDF 主要由扫描图片组成时，直接文本抽取通常为空或极少，导致导入价值接近零

这里的难点不在“识别 PDF”本身，而在于 OCR 方案选择：
- 直接绑定某个 OCR SDK 或云 API，会把库和单一供应商、运行环境、密钥模型耦合得很重
- 扫描版 PDF 的 OCR 往往依赖系统层工具和语言包，不适合默认硬塞进纯库运行时

因此更合适的方向是：库定义一个 OCR bridge 配置，由调用方提供本地 OCR 命令；库只负责在合适时机调用它，并把 OCR 结果继续送入现有分块、embedding、存储流程。

## Goals / Non-Goals

**Goals：**

- 支持扫描版/图片型 PDF 的 OCR 导入
- 保持文本型 PDF 的现有快路径和行为不变
- 用可配置 OCR bridge 适配不同本地 OCR 工具
- 在 OCR 不可用时给出清晰错误，而不是静默导入空内容

**Non-Goals：**

- 不内置特定第三方 OCR SDK 或云服务绑定
- 不实现版面分析、表格结构恢复或富文本重建
- 不支持密码保护 PDF、严重损坏 PDF 的特殊恢复
- 不做后台异步 OCR 队列

## Decisions

### 1. 采用“直接文本提取优先，OCR fallback 其次”的双路径

选择：
- 对 `.pdf` 先执行现有文本抽取
- 当抽取结果为空或低于最小可用阈值时，再尝试 OCR bridge

原因：
- 文本型 PDF 速度更快、质量更稳，不需要 OCR
- 扫描版 PDF 只在确实需要时才进入 OCR，避免无谓成本

备选方案：
- 所有 PDF 一律走 OCR：成本高，而且会降低文本型 PDF 质量
- 完全分成两类 source：对调用方不友好，还会增加 API 复杂度

### 2. OCR 通过可配置本地 bridge 命令接入

选择：
- 在根配置中新增 OCR bridge 配置
- 调用方提供命令、参数模板、环境变量和可选工作目录
- 库负责把 PDF 路径和临时输出路径注入命令参数，并读取 OCR 输出文本

原因：
- 避免绑定具体 OCR 供应商或 SDK
- 用户可以接入自己环境中已有的 `ocrmypdf`、`tesseract` 包装脚本或其他本地 OCR 工具
- 与已有有道桥接导入的设计思路一致

备选方案：
- 直接绑定某个 Go OCR 库：生态成熟度和跨平台稳定性不确定
- 直接绑定云 OCR：会引入外部网络、密钥、计费和稳定性耦合

### 3. OCR 输出统一收敛为纯文本文件

选择：
- bridge 命令输出一个临时文本文件，库读取该文本并继续走现有 `Document -> chunk -> embedding` 流程

原因：
- 不改动后续 RAG 管线
- 降低 OCR 结果结构化解析复杂度

备选方案：
- 让 bridge 直接返回 JSON 或富结构页面结果：会扩大首版范围

### 4. 缺少 OCR 配置时，扫描版 PDF 返回清晰错误

选择：
- 若 PDF 文本抽取不足且未配置 OCR bridge，返回明确的 OCR-required 风格错误

原因：
- 比静默导入空文本更可诊断
- 调用方能明确知道“这是扫描件，需要 OCR”

## Risks / Trade-offs

- [OCR bridge 命令格式差异大] → 只定义最小桥接契约：输入 PDF 路径、输出文本路径、命令退出码
- [OCR 速度慢] → 仅在文本提取不足时触发 OCR fallback
- [OCR 输出质量不稳定] → README 明确说明结果质量取决于用户配置的 OCR 工具和语言包
- [跨平台路径与命令行为差异] → 通过参数模板和环境变量配置，把平台差异交给调用方自定义

## Migration Plan

1. 新增 OCR bridge 配置类型与校验逻辑
2. 在 PDF loader 中接入“文本提取优先，OCR fallback”流程
3. 增加文本型 PDF、扫描型 PDF、缺失 OCR 配置等回归测试
4. 更新 README 中文说明

回滚策略：
- 回滚代码即可恢复当前“仅文本型 PDF”行为
- 无额外数据迁移
